# 블로그 초안 만들기

## 이 스킬은 블로그 레포 안에서만 돈다

다른 프로젝트(특히 회사 프로젝트) 세션에서 블로그 글을 쓰면, **그 세션의 컨텍스트에
사내 코드와 내부 정보가 들어 있는 상태로 공개될 글을 만들게 된다.** 아무리 조심해도
무의식적으로 새어 나갈 수 있고, 한 번 발행되면 되돌리기 어렵다.

그래서 규칙은 하나다:

> **글은 언제나 이 블로그 폴더에서 연 세션에서 쓴다.**
> 다른 세션이 이 폴더 경로를 알려주더라도, 그 세션에서 직접 쓰지 않는다.

작업하다 남길 거리가 생겼으면, 그 세션에서는 **한두 줄 메모만** 챙겨 나오고
(무엇을 알게 됐는지 / 참고 링크) 이 폴더에서 새 세션을 열어 여기서 쓴다.
`scripts/blog.mjs` 도 레포 밖에서 실행하면 거부한다.

시작할 때 위치를 확인한다:

```bash
pwd
```

`/Users/seongmun/Documents/github-blog` 가 아니면 **여기서 멈추고**,
블로그 폴더에서 세션을 새로 열라고 안내한다. 대신 써주지 않는다.

## 1. 무엇을 쓸지 듣는다

이 세션은 원래 작업의 맥락을 갖고 있지 않다. 사용자에게 듣는 것부터 시작한다.
길게 인터뷰하지 말고, 사용자가 풀어놓게 두고 필요한 것만 되묻는다.

- 무엇을 하려다가 뭐가 막혔는지
- 어떻게 풀렸는지, 왜 그렇게 동작하는지
- 참고한 문서 링크

사용자가 대화 내용이나 메모를 붙여넣으면 그걸 재료로 쓴다.

`ref/` 에 참고 자료(다른 AI 와 나눈 대화 내보내기, 강의 노트, PDF)가 있을 수 있다.
커밋되지 않는 폴더이므로 재료로만 쓴다. 관련 있어 보이면 확인한다:

```bash
ls ref/
```

**그대로 옮기지 않는다.** 이해한 내용을 사용자의 말로 다시 쓴다.
`ref/` 자료에도 회사 정보가 섞여 있을 수 있으니 그대로 통과시키지 않는다.

강의를 듣고 한 섹션을 정리하는 경우라면 이 스킬 대신 `/blog-lecture` 를 쓴다.
섹션·태그·제목 규칙이 거기에 고정돼 있다.

## 2. 남길 가치가 있는지 판단한다

기준은 하나다.

> **6개월 뒤의 내가 읽고 바로 써먹을 수 있는가.**

남길 만한 것:
- 문서에 없거나 찾기 어려웠던 동작, 제약, 함정
- 처음 접근이 틀렸고 왜 틀렸는지 알게 된 경우
- 개념 하나를 제대로 이해하게 된 대화
- 선택지를 비교하고 이유를 붙여 하나를 고른 판단

남기지 말 것:
- 공식 문서를 옮긴 내용 (링크 하나면 충분하다)
- 그 프로젝트에서만 통하는 설정값, 일회성 삽질
- 결론 없이 "해봤다"로 끝나는 기록

기준을 못 넘으면 그렇다고 말한다. 억지로 만들지 않는다.

## 3. 회사 정보를 걷어낸다

블로그는 **공개**된다. 사용자가 회사 작업 얘기를 꺼냈다면, 다음이 글에 들어가지 않게 한다:

- 사내 코드 원문, 내부 모듈/테이블/필드 이름, 사내 URL·호스트·엔드포인트
- 서비스명, 고객사명, 고객 데이터, 지표 수치
- 토큰·키·자격증명

익명화하는 게 아니라, 같은 원리를 보여주는 **새 최소 재현 예제를 짓는다.**
그렇게 다시 쓸 수 없는 내용이면 글로 만들지 않는다. 애매하면 사용자에게 묻는다.

## 4. 확인받는다

한 번에 정리해서 보여주고 확인받는다.

- **섹션** — 아래 넷 중 하나. URL 의 첫 경로가 된다.
  | 섹션 | key | 무엇을 담나 |
  | --- | --- | --- |
  | 프로젝트 | `project` | 만들면서 부딪힌 것들. 왜 그렇게 만들었는지까지 |
  | Study | `study` | 공부 기록, Claude와의 대화에서 건진 인사이트 |
  | 자격증 | `cert` | 준비 과정, 정리한 개념, 시험 후기 |
  | 논문 | `paper` | 읽은 논문을 내 말로 다시 정리한 기록 |
- **제목** (한글)
- **slug** (URL 이 된다. 영문 소문자 + 하이픈)
- **한 줄 요약** (목록과 검색 결과에 보이는 description)
- **태그** (선택) — 섹션 안에서 주제를 더 잘게 나눌 때만. 없어도 된다.

## 5. 글을 쓴다

어시스턴트 말투(`~인 것 같습니다`, `~하시면 됩니다`)를 남기지 않는다.
한국어, 담백한 평서체(`~다`)로 쓴다.

기본 구조 — 내용에 안 맞으면 바꿔도 된다:

```markdown
어쩌다 이걸 알게 됐는지 두세 문장. 배경을 길게 깔지 않는다.

## 문제

무엇을 하려다 뭐가 막혔는지. 가능하면 최소 재현 코드.

## 알게 된 것

핵심. 왜 그렇게 동작하는지까지 쓴다. 결론만 쓰면 나중에 응용이 안 된다.

## 정리

다음에 같은 상황을 만나면 무엇을 먼저 볼지, 한 문단.

## 참고

- [문서 제목](URL)
```

코드 블록에는 언어를 표시한다(` ```ts `). **확인하지 않은 코드는 넣지 않는다.**
이 레포에서 세션을 열었으므로 임시 디렉터리에서 직접 돌려보고 확인할 수 있다.


## 모를 만한 용어에는 툴팁을 단다

독자가 단어 하나에서 막히면 그 아래는 안 읽힌다. 한 줄로 설명되는 건 툴팁으로,
문단이 필요한 건 툴팁 + 보충 개념 절 링크로 처리한다. **`/blog-terms` 를 읽고 적용한다.**

## 다이어그램을 넣는다

블로그는 보여주는 매체다. **구조·흐름·비교가 나오는 글에는 그림을 최소 하나 넣는다.**
표와 코드블록만으로 끝내지 않는다.

**`/blog-diagram` 스킬을 읽고 그린다.** 무엇을 그릴지 고르는 기준, mermaid 문법,
이 레포에서 실제로 깨졌던 함정(한글 라벨 잘림, 괄호 파싱, 테마 색), 렌더 확인 방법이 거기 있다.

## 6. 저장한다

파일을 직접 쓰지 말고 스크립트를 쓴다. frontmatter 형식과 태그 검증을 스크립트가 책임진다.

```bash
node scripts/blog.mjs new \
  --section study \
  --title "제목" \
  --slug my-post-slug \
  --description "한 줄 요약" \
  --tags "태그1,태그2" \
  --body-file - <<'EOF'
본문
EOF
```

`draft: true` 로 저장되므로 배포되지 않는다.
새 섹션이 필요하면 `src/data/sections.ts` 에 먼저 추가한다 (스크립트가 그 파일을 읽는다).

## 7. 마무리

미리보기 방법을 한 줄로 알린다: `npm run dev` → `http://localhost:4321/<섹션>/<슬러그>/`
발행은 `/blog-publish` 로 한다. 여기서 커밋·푸시하지 않는다.

**주제가 바뀌면 여기까지다.** 같은 주제를 더 파고들거나 방금 쓴 글을 고치는 것은 괜찮다.
다른 주제의 글을 써달라는 요청을 받으면 쓰지 말고, 새 세션을 열라고 안내한다.
