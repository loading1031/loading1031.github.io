# 용어 툴팁

읽는 사람이 모르는 단어 하나에서 막히면 그 아래는 다 안 읽힌다.
그렇다고 모든 용어를 본문에서 설명하면 글이 늘어진다. **두 갈래로 나눈다.**

| 상황 | 방법 |
| --- | --- |
| 한 줄로 설명되는 용어 | 툴팁만 |
| 문단 이상 필요한 용어 | 툴팁 + 눌러서 **보충 개념** 절로 이동 |

새 문법은 없다. 마크다운이 원래 갖고 있는 **링크 title** 을 쓴다.

## 1. 툴팁만 — `<abbr>`

```markdown
<abbr title="Multi-Version Concurrency Control. 행을 덮어쓰는 대신 여러 버전을 두고, 읽는 쪽에 맞는 버전을 골라 주는 방식.">MVCC</abbr>
```

인라인 HTML 이라 마크다운 안에서 그대로 쓸 수 있다 (블록이 아니므로 빈 줄 문제 없음).
`title` 은 빌드 때 `data-tip` 으로 옮겨지고 점선 밑줄이 붙는다.

## 2. 툴팁 + 자세히 — 앵커 링크에 title

```markdown
이 두 단계를 [가시성 검사](#스냅샷과-가시성-검사--select-가-버전을-고르는-법 "여러 버전 중 지금 이 트랜잭션에게 어느 것이 보여야 하는지 판정하는 절차")라고 부른다.
```

`#` 으로 시작하는 링크에 title 이 있으면 툴팁 + 클릭 이동이 된다.
**대상 절은 글 아래쪽 `## 보충 개념` 안에 둔다.**

### 앵커 id 는 추측하지 말고 확인한다

제목을 소문자화하고 공백을 `-` 로, 문장부호는 제거해서 만들어진다.
한글·괄호·`/` 가 섞이면 헷갈리므로 렌더된 HTML 에서 직접 본다.

```bash
curl -s http://localhost:4321/<섹션>/<슬러그>/ | grep -o '<h[23] id="[^"]*"'
```

깨진 링크가 없는지도 확인한다. `<섹션>/<슬러그>` 만 바꿔서 그대로 실행한다.

```bash
node -e '
const u = "http://localhost:4321/study/database/section-2-acid/";
fetch(u).then(r => r.text()).then(h => {
  const ids = new Set([...h.matchAll(/<h[1-6] id="([^"]+)"/g)].map(m => m[1]));
  const body = h.slice(h.indexOf(String.fromCharCode(105,100,61,34) + "article"));
  const links = [...new Set([...body.matchAll(/href="#([^"]+)"/g)].map(m => decodeURIComponent(m[1])))];
  const bad = links.filter(l => !ids.has(l));
  console.log(bad.length ? "깨진 링크: " + bad.join(", ") : "앵커 링크 정상 (" + links.length + "개)");
});'
```

## 3. 툴팁을 달았으면 본문에서 또 설명하지 않는다

가장 흔한 실수다. 툴팁을 붙여 놓고 본문에도 같은 설명을 괄호로 또 쓴다.
**둘 중 하나만 남긴다. 웬만하면 툴팁만 남기고 본문에는 단어만 쓴다.**

```markdown
<!-- ❌ 툴팁에 있는 설명을 본문에서 반복 -->
(여러 버전 중 무엇을 보여줄지 고르는 절차가 [가시성 검사](#앵커 "여러 버전 중 어느 것이
보여야 하는지 판정하는 절차")다.)

<!-- ✅ 단어만 쓴다. 뜻은 툴팁이 말한다 -->
[가시성 검사](#앵커 "여러 버전 중 어느 것이 보여야 하는지 판정하는 절차") 결과에 따라
같은 체인을 거슬러 올라가 이전 버전을 재구성한다.
```

예외는 하나다. **앞 문단이 그 개념의 동작을 이미 풀어썼고, 거기에 이름을 붙이는 경우.**
이건 반복이 아니라 명명이다.

```markdown
힙에는 "누가 만들고 누가 지웠나"만 적혀 있고, "그 누가 성공했는지"는 pg_xact 에 따로 있다.
이 두 단계가 [가시성 검사](#앵커 "...")다.
```

초안을 다 쓴 뒤 툴팁이 달린 용어를 하나씩 훑으면서 **그 주변 문장이 툴팁과 같은 말을
하고 있지 않은지** 확인한다.

## 4. 무엇에 달지

- **처음 나오는 자리에만** 단다. 같은 용어에 매번 달면 지저분하다.
- 독자가 **모를 법한데 본문 흐름상 설명하기 애매한** 것에 단다.
- 툴팁 문구는 **한 문장.** 두 문장이 넘어가면 보충 개념 절로 뺄 신호다.
- 툴팁에 "~입니다" 같은 말투를 쓰지 않는다. 본문과 같은 평서체.
- 다이어그램 라벨에는 툴팁을 달 수 없다. 그림 안에서 설명이 필요하면
  라벨 자체를 자기설명적으로 고치거나, 그림 바로 아래 문단에서 풀어 준다.

## 5. 확인

- `npm run dev` 로 열어 마우스를 올려 본다. 말풍선은 **용어 아래쪽**으로 열린다.
  (위로 열면 앵커로 점프했을 때 화면 밖으로 잘린다. 그래서 아래로 고정해 뒀다.)
- 누르면 보충 개념 절로 내려가는지 확인한다.
- 터치 기기에서는 말풍선을 띄우지 않고 **바로 이동**한다 (`@media (hover: none)`).
  그래서 링크형 용어는 눌렀을 때 갈 곳이 반드시 있어야 한다.

## 6. 구현 (건드릴 일 있으면)

- `src/utils/rehypeTermTooltips.ts` — `title` → `data-tip` 이동, 클래스 부여.
  인라인 `<abbr>` 은 이 시점에 raw 문자열이라 정규식으로 따로 처리한다.
- `src/styles/typography.css` 의 `[data-tip]` — 말풍선 모양.
  목록 안에서 가로로 잘리지 않게 `ul:has([data-tip])` 의 overflow 를 풀어 둔다.
