# 발표 자료

한 주제를 끝까지 파고든 세션의 마무리로, 그 내용을 남 앞에서 말할 수 있는 형태로 굽는다.
산출물은 **claude.ai 아티팩트 한 장** — 좌측에 목차, 본문은 절 단위로 스크롤되는 덱이다.
슬라이드가 아니라 **스크롤 문서**인 이유는, 그림 하나가 반 페이지를 먹고
표가 자주 들어가서 16:9 칸에 안 들어가기 때문이다.

## 0. 전제

- **이 레포에서 연 세션에서만 만든다.** `pwd` 로 확인한다. 이유는 블로그 글과 같고,
  덱은 **링크 하나로 남에게 건네지는 물건**이라 한 단계 더 위험하다.
  회사 코드·내부 수치가 섞인 세션에서는 만들지 않는다.
- **한 주제 = 한 세션.** 덱은 그 세션에서 이미 검증한 것을 재료로 쓴다.
- **덱에 들어가는 수치는 전부 실제로 돌려서 받은 값이다.** 표를 하나 넣을 때마다
  "이 숫자가 어느 컨테이너에서 어떤 쿼리로 나왔는지" 말할 수 있어야 한다.
  발표는 질문을 받는 자리다. 추측으로 채운 칸은 반드시 거기서 걸린다.

재료가 아직 없으면 덱부터 만들지 않는다. 먼저 질문하고, 돌려 보고, 확인한 다음에 그린다.
실제로 잘 나온 순서는 늘 이랬다 — **개념 질문 → 컨테이너에서 확인 → "이 내용으로 그려줘"**.

## 1. 목차를 먼저 확정한다

사용자에게 절 목록을 받는다. 없으면 제안하고 고르게 한다.

- **절은 6~8개.** 한 절이 한 덩어리다.
- **첫 절은 "왜 필요한가".** 구조부터 들이밀지 않는다.
- **마지막 절은 "질문거리".** 이 세션에서 **실제로 내가 막혔던 질문**을 넣는다.
  발표에서 가장 잘 먹히는 절이고, 이미 대화에 다 있으므로 새로 만들 것도 없다.
- 익숙한 그림에서 출발해 낯선 층위로 내려간다 — B+트리(익숙) → 페이지(낯섦) 순서지,
  그 반대가 아니다.
- **절 제목과 목차 항목은 용어로 단다.** "파티션 프루닝(가지치기)", "유니크 제약과 FK" 처럼
  보자마자 무슨 절인지 알아야 한다. "답이 없는 파티션은 열지 않는다" 같은 풀어 쓴 주장 문장은
  한 번 더 해석해야 해서 목차에서 안 읽힌다. 주장은 절 안의 `p.lead` 에 둔다.
  낯선 영어 용어는 한국어를 괄호로 붙인다.

## 2. 골격을 먼저 배포한다

`template.html` 을 복사해 **사이드바 목차 + 절 제목 + 각 절의 `.slot` 자리**만 채운 채로
아티팩트를 publish 한다. 본문은 비운다.

```
Artifact(file_path=<작업파일>, icon="slides", title="<덱 제목>")
```

한 번에 다 만들려고 하지 않는다. 절 하나가 SVG 하나에 표 두 개다 — 다 쓰면 중간에 끊긴다.
골격이 먼저 링크로 나가 있어야 사용자가 목차를 보고 순서를 바꿀 수 있고,
**아티팩트에 댓글로 지시**할 수 있다.

이후 모든 수정은 **같은 url 로 republish** 한다.
세션이 바뀐 뒤라면 `action: "read"` 로 먼저 읽고, 돌아온 파일을 고쳐서 올린다.

## 3. 절 하나씩 채운다

`.slot` 을 지우고 `.body` 로 바꾼다. 한 절의 뼈대는 늘 같다.

| 순서 | 무엇 |
| --- | --- |
| 0 | `h4.subhead` — 소절 이름. **목차 하위 항목과 글자까지 같게.** 목차의 앵커 id 도 여기 단다 |
| 1 | `p.lead` — **결론 한 줄.** 짧게. "PK 에는 파티션 키가 들어가야 한다" |
| 2 | 왜 그런지 두세 문장 |
| 3 | `figure` — 그림 |
| 4 | 실측 표 또는 `.cmp` 비교 카드 |
| 5 | 한계·곁가지 한 문단 (`p.note-inline`) |

절을 채우기 전에 그 절의 개념이 흔들리면 **먼저 묻고 확인한다.** 그린 다음에 고치는 것보다 싸다.

## 4. 그림

**덱에서는 mermaid 를 쓰지 않는다. 인라인 SVG 로 그린다.**
블로그(`/blog-diagram`)와 갈리는 지점이다 — 덱에는 빌드 파이프라인이 없고,
탭 전환·단계 애니메이션·노드 확대처럼 mermaid 가 못 하는 것이 필요하다.

공통 규칙:

- `viewBox="0 0 760 H"`, `.scroller` 로 감싸고 `min-width: 620px`
- 색은 직접 쓰지 않는다. 클래스로만 — `.box` `.plain`(배경) `.hl` `.hlt`(강조)
  `.line` `.dash` `.acc`(선) `.rule`(칸선) / `.m`(모노) `.f`(흐리게)
- `role="img"` + `aria-label` 에 **그림이 말하려는 바를 문장으로** 적는다
- 화살표는 `<marker>` 를 절마다 다른 id 로 정의한다 (id 가 겹치면 조용히 엉킨다)

### 세 가지 장치

**탭 (`.switch`)** — 같은 대상을 **층위를 바꿔** 볼 때. 비교가 아니다.
논리(B+트리) → 물리(블록) → 확대(페이지 한 장) 처럼, 같은 것의 다른 얼굴일 때만 쓴다.
`data-tabs="2"` / `"4"` 로 개수를 맞춘다. 패널은 첫 장 빼고 `hidden`.

**단계 애니메이션 (`.anim`)** — **순서 자체가 요점**일 때만. 결과 그림으로 충분하면 쓰지 않는다.
SVG 안의 id 규칙을 지키면 `template.html` 의 러너가 그대로 돈다.

| id | 무엇 |
| --- | --- |
| `ix-<키>-<리프>-<슬롯>` / `it-…` | 인덱스 칸 / 그 안의 글자 |
| `hb-<키>-<블록>` | 힙 블록 |
| `hs-<키>-<블록>-<슬롯>` / `ht-…` | 힙 행 / 그 글자 |
| `bm-<키>-<비트>` / `bt-…` | 비트맵 칸 / 그 글자 |
| `beam-<키>` | 인덱스→힙 이동선 (좌표는 러너가 계산한다) |
| `ro-<키>` | 아래 읽어 주는 숫자 |

단계는 `STEPS["<키>"]` 배열이고, 각 원소는 `{ix, heap, slots, bit, sort, phase}` 중 필요한 것만 담는다.
지나간 칸은 `.done`, 지금 칸은 `.now` 가 붙는다.

**비교 카드 (`.cmp`) · 표** — 수치. 표의 요점 행에는 `class="on"` 을 준다.

### 실제로 걸렸던 함정

- **두 구조를 "겹쳐 보기" 로 만들면 안 읽힌다.** 같은 트리를 두 번 그리는 대신
  **좌: 트리 전체 / 우: 노드 하나를 페이지로 확대** 로 놓는다. 그래야 트리 그림에서
  칸 사이에 끼어 있던 경계값이 페이지 안에서 한 줄씩 어떻게 저장되는지가 보인다.
- **결과만 보여주지 않는다.** "힙 블록 몇 개를 읽었다" 로 끝내면 질문이 바로 나온다.
  인덱스에서 힙으로 **건너가는 경로**를 그린다.
- **라벨에 조건식을 그대로 쓰지 않는다.** `id > 500000` 이 아니라
  "파일 뒤쪽에 몰려 있던 행" 이라고 쓴다. 조건만 쓰면 그게 뭘 뜻하는지 아무도 모른다.
- **약어는 한 번은 풀어 쓴다.** `blk` = block, `lp` = line pointer.
  그리고 lp 를 "주소" 같은 말로 바꿔 부르지 않는다 — 용어를 섞으면 거기서 질문이 터진다.
- **숫자에는 단위를 붙인다.** "80에서 40으로 줄었다" 는 무슨 배수인지 알 수 없다.
- **그래프의 축에 무엇이 실려 있는지 쓴다.** 가로축이 시간인지 LIMIT 인지.

## 5. 발표용으로 덜어낸다

블로그 글은 읽는 것이고 덱은 **말하면서 넘기는 것**이다. 기준이 다르다.

- 한 단계 더 깊은 곁가지는 뺀다. 재미있어도 뺀다 (예: 비트맵이 `work_mem` 을 넘겨
  lossy 로 떨어지는 이야기 — 맞는 내용이지만 발표에서는 흐름을 끊는다).
- **제목은 용어, 주장은 결론 한 줄.** 제목·목차에 주장 문장을 쓰지 않는다(1장 참고).
  결론 문장도 이유까지 한 문장에 몰아넣지 않는다. "한 파티션의 B-tree 는 다른 파티션에 같은 값이
  있는지 모른다. 그래서 PK 에 파티션 키가 들어가야 한다" 가 아니라 "PK 에는 파티션 키가 들어가야 한다".
  이유는 다음 문단에서 말한다. 에러 문구를 본문에 줄줄이 인용하지 않는다.
  (섹션6 파티셔닝 덱에서 "제목이 풀어 써서 바로 이해가 안 된다", "목차 소제목과 본문이 다르다"는
  피드백을 받고 바꾼 규칙이다.)
- **질문 절의 질문은 전제가 틀리지 않았는지 본다.** "열 기반 DB 에는 왜 인덱스가 없나" 는
  전제부터 틀렸다. "열 기반 DB 는 인덱스로 범위를 못 찾나" 가 맞는 질문이다.

## 6. 화이트 고정

`:root { color-scheme: light }` 로 고정하고 다크 모드 분기를 두지 않는다.
**뷰어가 다크 테마여도 흰 화면으로 나가야 한다** — 빔프로젝터와 화면 공유에서
어두운 배경은 그림 선이 날아간다. 블로그는 테마를 따라가지만 덱은 따라가지 않는다.

## 7. 블로그 글과의 관계

같은 재료를 쓰지만 **서로 자동 변환하지 않는다.**

| | 블로그 글 | 발표 덱 |
| --- | --- | --- |
| 읽는 사람 | 6개월 뒤의 나 | 지금 앞에 앉은 사람 |
| 그림 | mermaid (빌드가 SVG 로 굽는다) | 인라인 SVG + 상호작용 |
| 색 | 테마를 따라간다 | 화이트 고정 |
| 깊이 | 곁가지도 남긴다 | 흐름을 끊는 것은 뺀다 |

덱을 만들다 새로 검증한 내용은 **같은 주제의 글**에만 반영한다
(`/blog-capture` · `/blog-lecture`). 다른 주제의 글을 새로 만들지 않는다.

## 8. 넘기기 전에

- [ ] 표의 모든 수치가 실제로 돌려서 나온 값인가. 어디서 나왔는지 말할 수 있는가
- [ ] 회사 코드·내부 정보·개인 정보가 한 글자도 없는가
- [ ] 모든 SVG 에 `aria-label` 이 있는가. marker id 가 겹치지 않는가
- [ ] 탭 패널이 첫 장 빼고 `hidden` 인가. 목차 링크가 전부 실제 id 로 가는가
- [ ] 절 제목·목차가 용어인가. 목차 하위 항목과 본문 `h4.subhead` 가 글자까지 같은가
- [ ] 다크 테마 브라우저에서 열어도 흰 화면인가
- [ ] 좁은 화면에서 목차가 가로 스크롤로 접히는가
- [ ] 마지막 절의 질문들이 **내가 실제로 막혔던 것**인가
